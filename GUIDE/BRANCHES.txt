THE SHORT ANSWER
----------------
Take main. Everything is there - source, documentation and
prebuilt images. dev is where the work happens, and right now it
holds exactly the same files.


main
----
The branch you want.

  Full source            kernel configuration, the C library,
                         init, the shell, all 107 commands, the
                         image tools and the self-test
  README.md              the long description, in Korean
  README.en.md           the same document in English
  GUIDE/USAGE.txt        how to run it, log in and build it
  GUIDE/BRANCHES.txt     this file
  dist/                  images ready to burn or attach:
                           linux-LP_amd64.img.xz
                           test_a_123_LPzero2W_linux.img.xz
                           test_a_123_LPzero2W_linux-utm.zip
                           SHA256SUMS.txt

Start with GUIDE/USAGE.txt if you want to run it, and README.en.md
if you want to understand it.


dev
---
The development branch. Everything above was committed here first
and then merged into main, so at the moment the two branches
contain identical files.

It is kept for the commit history. Seventy-odd commits, each with
a message explaining what was wrong and why the fix is shaped the
way it is - the part that a squashed merge would throw away. When
you want to know why something is the way it is, read the log
here.

The most recent work, newest first:

  * The shell had loops and no way out of one - break and continue
    exist now. Alongside them: guard's CPU-hog notice reaches the
    log and not only the console, and the self-test's signature
    check tests the signature rather than the file-format check in
    front of it.

  * Drives that get plugged in, and drives the system keeps -
    automount and storage.

  * Phase 3: our own firmware boots Linux off the card.

  * Phase 2: the board can now say where it died.

  * Every lp_log message was a continuation record, so no reader
    ever saw it. A kmsg write that does not end in a newline is a
    continuation: the kernel leaves the record unfinalised and
    nothing displays it. Fixed alongside it: sleep (33 seconds
    became 3003), top -n, test with spaced numeric operands, and
    the shell gained $!.

  * The self-test learns the difference between broken and not
    present.

  * SSH never worked, and the tests that would have said so did
    not exist.

  * The amd64 image shipped 43MB of ARM, and nothing was looking.

New work goes on a branch of its own, gets built, has to pass
tests/selftest.sh, and only then reaches main.


WHO WROTE ALL OF IT

Claude Code, Anthropic's coding agent, working from the repository

WHAT IS DELIBERATELY NOT IN GIT
-------------------------------
All of it is regenerated by a build:

  blobs/           Broadcom GPU firmware  (tools/fetch-blobs.sh)
  sdcard/          assembled card images  (tools/mksdcard.sh)
  keys/            update signing keys. The private key must never
                   leave your own machine
  .build/          kernel source, sysroot, staging
  sdk/ repo/       generated by tools/build-sdk.sh and mkpkg.sh

dist/ would normally be on that list too. The three images are
checked in anyway, so that somebody can download the system and
run it without setting up a cross toolchain first. They are still
reproducible with ./tools/mkdist.sh, and the checksums beside them
are written by the same script that writes the images.


WHERE THINGS STAND
------------------
Verified: the amd64 image passes all 51 checks in
tests/selftest.sh on real QEMU boots.

Not verified: anything on physical Raspberry Pi hardware - the
WiFi association, the thermal sensors, the hardware watchdog. And
none of the security work has been audited by anybody outside this
repository. GUIDE/USAGE.txt has the full list under BEFORE YOU
RELY ON THIS, and it is worth reading before you deploy this
anywhere real.

The original plan is now finished. The last two items - the
bare-metal firmware phases that had been left open - are done:

  Phase 2   exception vectors, the interrupt controllers and a
            panic handler that decodes ESR/FAR/ELR and walks the
            call path
  Phase 3   an Arasan SDHCI driver, MBR and FAT32 reading, device
            tree rewriting, and the handover to Linux

So the whole chain below Linux is ours except the two Broadcom
blobs the GPU boot ROM demands. One gap is stated rather than
hidden: the loader does not apply device tree overlays, which is
invisible on real hardware (start.elf hands us a tree that already
has them) and named out loud where it is not.

dev
---
개발 브랜치입니다. 위의 내용은 전부 여기서 먼저 커밋한 뒤 main 으로
합쳤기 때문에, 지금 두 브랜치의 파일은 완전히 같습니다.

그래도 남겨둔 이유는 커밋 기록 때문입니다. 일흔 몇 개의 커밋마다
무엇이 잘못돼 있었고 왜 그런 모양으로 고쳤는지가 적혀 있습니다.
squash 로 합치면 사라지는 부분입니다. 무언가가 왜 그렇게 되어
있는지 궁금할 때 여기 로그를 보시면 됩니다.

가장 최근 작업부터:

  * 셸에 루프는 있는데 빠져나갈 방법이 없었다 - break 와 continue
    를 넣었다. 함께: guard 의 CPU 점유 경고가 콘솔뿐 아니라 로그에도
    남고, 셀프테스트의 서명 검사가 그 앞의 형식 검사가 아니라
    실제로 서명을 검사하게 되었다.

  * 꽂으면 붙는 드라이브와, 시스템이 계속 데리고 있는 드라이브 -
    automount 와 storage.

  * Phase 3: 우리 펌웨어가 카드에서 리눅스를 띄운다.

  * Phase 2: 보드가 어디서 죽었는지 말할 수 있게 되다.

  * lp_log 로 남긴 모든 메시지가 continuation 레코드였고, 그래서
    아무도 볼 수 없었다. 개행으로 끝나지 않는 kmsg 쓰기는
    continuation 이라, 커널이 레코드를 미확정 상태로 두고 어떤
    리더도 보여주지 않는다. 함께 고친 것: sleep(33초가 3003초로
    갔다), top -n, 공백이 붙은 숫자를 받는 test, 그리고 셸에
    $! 추가.

  * 셀프테스트가 고장난 것과 없는 것을 구별하게 되다.

  * SSH 는 한 번도 된 적이 없었고, 그걸 알려줄 테스트도 없었다.

  * amd64 이미지가 43MB 의 ARM 을 싣고 나갔는데 아무도 안 봤다.

새 작업은 별도 브랜치에서 하고, 빌드해서 tests/selftest.sh 를
통과시킨 뒤에야 main 으로 갑니다.


전부 누가 만들었나
------------------
Anthropic 의 코딩 에이전트인 Claude Code 가 저장소 주인의 지시를
받아 썼습니다. 커널 설정, C 라이브러리, init, 셸, 107개 명령어,

말하면, 판단 근거가 유난히 잘 남아 있고, 독립적인 검토를 받은 적은
없습니다.


깃에 일부러 넣지 않은 것
------------------------
전부 빌드로 다시 만들어지는 것들입니다.

  blobs/           Broadcom GPU 펌웨어  (tools/fetch-blobs.sh)
  sdcard/          조립된 카드 이미지   (tools/mksdcard.sh)
  keys/            업데이트 서명 키. 개인키는 절대 본인 컴퓨터를
                   벗어나면 안 됩니다
  .build/          커널 소스, sysroot, 스테이징
  sdk/ repo/       tools/build-sdk.sh 와 mkpkg.sh 가 만듭니다

dist/ 도 원래는 이 목록에 있어야 합니다. 그래도 이미지 세 개를
넣어둔 이유는, 크로스 툴체인을 갖추지 않은 사람도 받아서 바로
돌려볼 수 있게 하기 위해서입니다. ./tools/mkdist.sh 로 언제든 똑같이
다시 만들 수 있고, 옆에 있는 체크섬은 이미지를 만드는 그 스크립트가
같이 씁니다.


지금 어디까지 와 있나
---------------------
확인된 것: amd64 이미지가 QEMU 실제 부팅에서 tests/selftest.sh 의
51개 검사를 전부 통과합니다.

확인 안 된 것: 라즈베리파이 실물에서의 모든 것 — WiFi 연결, 온도
센서, 하드웨어 워치독. 그리고 보안 부분은 이 저장소 밖의 누구에게도
감사를 받지 않았습니다. 전체 목록은 GUIDE/USAGE.txt 의 "믿고 쓰기
전에"에 있고, 실제 어딘가에 올리기 전에 읽어보실 만합니다.

원래 계획은 이제 끝났습니다. 열어두었던 베어메탈 펌웨어 단계 둘이
완료되었습니다.

  Phase 2   예외 벡터, 인터럽트 컨트롤러, 그리고 ESR/FAR/ELR 를
            풀어 읽고 호출 경로까지 보여주는 패닉 핸들러
  Phase 3   Arasan SDHCI 드라이버, MBR 과 FAT32 읽기, 디바이스
            트리 재작성, 리눅스 인계

그래서 리눅스 아래의 사슬은 GPU 부트롬이 요구하는 Broadcom 블롭
둘을 빼면 전부 우리 것입니다. 한 가지는 감추지 않고 적어둡니다 -
로더가 디바이스 트리 오버레이를 적용하지 않습니다. 실기에서는
start.elf 가 이미 적용한 트리를 받으므로 드러나지 않고, 그렇지
않은 환경에서는 로더가 그 사실을 말합니다.
