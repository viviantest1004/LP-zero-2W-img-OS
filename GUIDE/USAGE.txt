WHAT THIS IS
------------
A small Linux distribution written from scratch. The kernel
configuration, the C library, init, the shell and all 108 commands
are original code. The kernel image is the whole system: the
userland is packed inside it and unpacks into RAM when the machine
boots.

  Whole system            one file, 11-23 MB
  RAM left after boot     480 MB free on a 512 MB board
  Boot time               about 10 seconds to a prompt
  Commands                107, every one written here
  SSH                     built in, public key only
  Python                  CPython 3.12 + pip, manylinux wheels work
  Firewall                on by default
  Licence                 MIT

Four things come from outside: the Broadcom blob the Raspberry Pi
GPU boot ROM insists on, and three cryptography implementations
(dropbear, wpa_supplicant, OpenSSL). Cryptography is the one thing
you should not write yourself, so it was deliberately borrowed.


WHO WROTE IT
------------
All of it was written by Claude Code, Anthropic's coding agent,
working from the repository owner's direction. That covers the
kernel configuration, the C library, init, the shell, the 105
commands, the build system, the self-test and the documentation.

Two things follow from that, and both are worth knowing. The
reasoning is unusually well recorded - the commit log explains why
each change was made, and the comments say what was tried and what
broke. And nobody independent has reviewed it, it has never run in
production, and it has no track record. Read BEFORE YOU RELY ON
THIS, further down, before you put it anywhere that matters.


BEFORE YOU RELY ON THIS
-----------------------
None of this is a reason to avoid the system. All of it is a
reason not to be surprised.

  * It is a hobby operating system, not a supported product.
    There is no security team, no CVE process, nobody on call.
    For anything that has to keep working, use Raspberry Pi OS
    Lite or Debian.

  * Real hardware is not verified. Everything was tested in QEMU.
    On a physical Pi Zero 2 W the WiFi association, the thermal
    sensors and the hardware watchdog have not been confirmed.
    Treat the arm64 image as untested on metal.

  * The security work has not been audited. Update signature
    checking, the firewall, the DNS and NTP hardening are all
    implemented and all reasoned about in the comments - and none
    of it has been reviewed by anybody else.

  * The C library is ours and it is not complete. It covers what
    the 108 commands need; anything else you compile against it
    may reach for a function that is not there. Ordinary Linux
    binaries run through the `run` command instead, against the
    glibc that ships with Python.

  * /data is the only thing that survives a reboot, and it is one
    partition on one card. Cards die. Copy off anything you care
    about.

  * dd to the wrong device destroys that device. Check /dev/sdX
    twice. It is the one mistake here that a reboot cannot undo.

  * No GUI, a small package set, no containers.

  * There are rough edges. A recent one: every message written
    through our own logger was invisible to dmesg for months,
    because a kmsg record with no trailing newline is a
    continuation the kernel never finalises. It surfaced by
    running the self-test end to end and asking why one check
    failed. Expect more of that kind.

What is verified: the amd64 image passes all 51 checks in
tests/selftest.sh on real QEMU boots.


WHICH IMAGE DO I WANT
---------------------
There is a download page, which is easier than reading this:

  https://viviantest1004.github.io/LP-zero-2W-img-OS/

The files themselves are in dist/ on the main branch.

  dist/linux-LP_amd64.img.xz
      An ordinary PC, or a desktop virtual machine - VMware,
      VirtualBox, QEMU/KVM, Hyper-V. UEFI boot.

  dist/test_a_123_LPzero2W_linux.img.xz
      Raspberry Pi Zero 2 W hardware and arm64 virtual machines.
      One image covers both, because it carries the uncompressed
      kernel the Pi's GPU reads and the EFI executable UEFI reads.

  dist/test_a_123_LPzero2W_linux-utm.zip
      arm64 virtual machines only (UTM, UTM SE, QEMU). Smaller,
      since a VM has no use for the GPU firmware.

Check what you downloaded before you use it:

  cd dist && sha256sum -c SHA256SUMS.txt


ON A RASPBERRY PI ZERO 2 W
--------------------------
  xz -d < dist/test_a_123_LPzero2W_linux.img.xz \
    | sudo dd of=/dev/sdX bs=4M conv=fsync status=progress

Replace /dev/sdX with your card, and check it before you press
return. Put the card in the board and power it up; /data grows to
fill the card on the first boot.


IN A VIRTUAL MACHINE
--------------------
Set the machine to UEFI boot. The MBR bootstrap is empty on
purpose, so a legacy BIOS will not start it.

amd64, QEMU:

  xz -d < dist/linux-LP_amd64.img.xz > lp.img
  qemu-system-x86_64 -m 1024 -bios /usr/share/OVMF/OVMF_CODE.fd \
    -drive file=lp.img,format=raw,if=virtio \
    -netdev user,id=n0,hostfwd=tcp::2222-:22 \
    -device virtio-net-pci,netdev=n0 -nographic

arm64, UTM or UTM SE: unzip the -utm.zip and attach the .img
inside it as the disk. Nothing else needs setting.

To give it a bigger disk, truncate -s 16G the image file. It is
sparse, so it only occupies what is written.


LOGGING IN
----------
There is one user: root. On the screen or the serial console you
get a prompt straight away.

Over SSH there are no passwords. Password authentication is not
compiled in at all - on a board facing the internet a password is
only a matter of time, so it was never offered as an option.
Public keys only:

  1. The first partition of the card or image is FAT32, so it
     opens on Windows, macOS and Linux. Put your public key into
     a file called authorized_keys there:

       cat ~/.ssh/id_ed25519.pub >> /media/BOOT/authorized_keys

     While that file exists it is the master copy and overwrites
     the device's own at every boot. That is deliberate: if /data
     is destroyed you can still get in by pulling the card and
     editing one file. Delete it from /boot if you would rather
     manage keys on the machine.

  2. Find the address with `ifconfig` on the console. DHCP is
     automatic; for a fixed address write network.conf on the boot
     partition.

  3. ssh root@192.168.0.42
     or, with the QEMU line above, ssh -p 2222 root@localhost

If it will not connect:

  authkey -l                which keys are accepted right now
  service status dropbear
  firewall status
  cat /data/log/auth        login records


PLUGGING A DRIVE IN
------------------
A USB stick or an external disk mounts itself. automount listens
to the kernel's uevent messages, so a drive appears under
/media/<name> within a moment of being plugged in, and is released
when it is pulled. It also scans once at startup for drives that
were already attached.

  automount -l            what is mounted right now
  automount -u <name>     release one

It never touches the disk the system booted from, and it mounts
nosuid,nodev - that filesystem was written by another machine.

/media is a temporary place. For a drive that should be at the
same path after every reboot, adopt it:

  storage                          what survives a reboot, and how
                                   full each place is
  storage adopt /dev/sdb photos    keep it at /mnt/photos
  storage format /dev/sdb backup   erase it, make ext4, then keep it
  storage forget photos            stop keeping it

An adopted drive is matched by its filesystem label, not its
device name, so it works in any port - sdb1 becomes sdc1 the
moment somebody plugs in a second drive first.

poweroff releases these before it unmounts /data, detaching
anything busy: a drive nobody can unmount must not become a
machine nobody can switch off.


WHERE THE SOURCE IS
-------------------
All of it is on the main branch. There are no per-architecture
source trees - arm64 and amd64 build from the same code.

  userland/     our C library, init, the shell, all 108 commands
    libc/         the C library, straight on top of the syscalls
    sh/           the shell
    init/         pid 1
    guard/        the watchdog daemon: CPU, memory, heat, power
    <name>/       one directory per command
    mkrootfs.sh   assembles the root filesystem
  kernel/       kernel configuration and build script
    lp-zero.config         arm64 (Raspberry Pi)
    lp-zero-amd64.config   amd64 (PC)
    build.sh               builds the kernel with our initramfs in it
  tools/        image assembly, SDK, package builder, QEMU runner
    mkdist.sh     builds all three distribution images
    mksdcard.sh   assembles one card image
    run-qemu.sh   boots it locally
  tests/        selftest.sh - 51 checks that run on the machine
  boot/         what lands on the FAT32 boot partition
  packages/     package definitions
  docs/         design notes
  GUIDE/        this folder
  dist/         the prebuilt images

README.en.md at the top of the repository is the long version in
English: what every command does, why the system does not fall
over, the security model, and the limits. README.md is the same
document in Korean.


BUILDING IT YOURSELF
--------------------
  sudo apt install clang lld llvm gcc-aarch64-linux-gnu \
       mtools dosfstools e2fsprogs xz-utils zip cpio bc \
       bsdextrautils qemu-system-arm qemu-system-x86 python3

arm64 (Raspberry Pi and arm64 VMs):

  ./tools/fetch-kernel.sh      # Linux source
  ./tools/fetch-blobs.sh       # Raspberry Pi GPU firmware
  make                         # userland
  make kernel                  # kernel + initramfs
  make sdcard-linux            # sdcard/lp-zero.img

amd64 (PC) - native, no cross compiler needed:

  make ARCH=amd64
  ( cd userland && LP_ARCH=amd64 LP_BINDIR=bin-amd64 \
      LP_ROOTFS_DIR=rootfs-amd64 \
      LP_CPIO_NAME=initramfs-amd64.cpio.gz \
      LP_HOSTNAME=linux-lp LP_OS_NAME=linux-LP ./mkrootfs.sh )
  LP_ARCH=amd64 LP_ROOTFS_DIR=rootfs-amd64 ./kernel/build.sh
  LP_ARCH=amd64 LP_ROOTFS_DIR=rootfs-amd64 \
      ./tools/mksdcard.sh --linux --uefi-only

All three distribution images at once:

  ./tools/mkdist.sh            # or: mkdist.sh amd64 | sd | utm

Intermediate build products go into .build/ beside the repository.
Move them with LPZERO_WORK=/mnt/big/lpzero if the disk is tight.

The update signing key, made once. Never put the private key on a
device; keys/ is in .gitignore:

  ./tools/sign-release.sh --new-key
  make
  ./tools/sign-release.sh kernel/out/Image


CHECKING A BUILD
----------------
tests/selftest.sh runs on the machine itself and prints one PASS
or FAIL line per check: boot, storage, SSH, Python, graphics,
security, error paths, redirection, logging, timing, and whether
the watchdog notices a process pinning a core.

  sh /path/to/selftest.sh

51 checks pass on the amd64 image as of this writing.

믿고 쓰기 전에
--------------
어느 것도 "그러니 쓰지 마세요"는 아닙니다. 전부 "그러니 놀라지
마세요"에 가깝습니다.

  * 지원되는 제품이 아니라 취미로 만든 운영체제입니다. 보안팀도,
    CVE 절차도, 대기하는 사람도 없습니다. 계속 돌아가야만 하는
    일에는 Raspberry Pi OS Lite 나 데비안을 쓰세요.

  * 보안 부분은 외부 감사를 받지 않았습니다. 업데이트 서명 검증,
    방화벽, DNS·NTP 위조 방지가 전부 구현돼 있고 주석에 근거도 적혀
    있지만, 다른 사람이 검토한 적은 없습니다.

  * C 라이브러리가 자체 구현이고 완전하지 않습니다. 108개 명령어에

  * 재부팅을 넘겨 남는 곳은 /data 하나뿐이고, 그건 카드 한 장의

    확인하세요. 여기서 재부팅으로 되돌릴 수 없는 실수는 이것뿐입니다.

  * GUI 없음, 패키지 적음, 컨테이너 안 됨.

  * 거친 구석이 남아 있습니다. 최근 사례 하나: 자체 로거로 남긴 모든
    메시지가 dmesg 에 몇 달 동안 보이지 않았습니다. 개행으로 끝나지
    않는 kmsg 레코드는 커널이 확정하지 않는 continuation 이기
    때문입니다. 셀프테스트를 끝까지 돌려보고 검사 하나가 왜
    실패하는지 물은 끝에 찾았습니다. 이런 것이 더 나올 거라고

가상머신에서
------------
UEFI 부팅으로 설정하세요. MBR 부트스트랩은 일부러 비워두었기 때문에
legacy BIOS 로는 뜨지 않습니다.

amd64, QEMU:

  xz -d < dist/linux-LP_amd64.img.xz > lp.img
  qemu-system-x86_64 -m 1024 -bios /usr/share/OVMF/OVMF_CODE.fd \
    -drive file=lp.img,format=raw,if=virtio \
    -netdev user,id=n0,hostfwd=tcp::2222-:22 \
    -device virtio-net-pci,netdev=n0 -nographic

arm64, UTM 또는 UTM SE: -utm.zip 을 풀고 안에 있는 .img 를 디스크로
붙이면 됩니다. 그 밖에 설정할 것은 없습니다.

디스크를 키우려면 이미지 파일을 truncate -s 16G 하면 됩니다. 파일이
sparse 라서 실제로 쓰는 만큼만 차지합니다.


로그인
------
사용자는 root 하나입니다. 화면이나 시리얼 콘솔에서는 바로 프롬프트가
나옵니다.

SSH 는 비밀번호가 없습니다. 비밀번호 인증은 아예 컴파일하지
않았습니다. 인터넷에 물린 보드에서 비밀번호는 시간 문제라서 선택지로
두지 않았습니다. 공개키만 씁니다.

  1. 카드(또는 이미지)의 첫 번째 파티션은 FAT32 라서 윈도우, 맥,
     리눅스 어디서나 열립니다. 거기 authorized_keys 파일에 공개키를
     넣으세요.

       cat ~/.ssh/id_ed25519.pub >> /media/BOOT/authorized_keys

     이 파일이 있는 동안은 그쪽이 원본이고, 부팅할 때마다 기기 안의
     것을 덮어씁니다. 일부러 그렇게 했습니다. /data 가 망가져도
     카드만 뽑아서 파일 하나 고치면 들어갈 수 있어야 하기
     때문입니다. 기기에서 관리하고 싶으면 /boot 에서 그 파일을
     지우세요.

  2. 콘솔에서 ifconfig 로 주소를 확인합니다. DHCP 는 자동이고,
     고정 주소를 쓰려면 부트 파티션에 network.conf 를 두세요.

  3. ssh root@192.168.0.42
     위 QEMU 설정이면 ssh -p 2222 root@localhost

안 될 때:

  authkey -l                지금 허용된 키
  service status dropbear
  firewall status
  cat /data/log/auth        로그인 기록


드라이브를 꽂으면
-----------------
USB 메모리든 외장 하드든 꽂으면 알아서 붙습니다. automount 가 커널의
uevent 를 듣고 있다가 잠깐 사이에 /media/<이름> 에 마운트하고, 빼면
정리합니다. 부팅할 때 이미 꽂혀 있던 것도 한 번 훑습니다.

  automount -l            지금 뭐가 붙어 있나
  automount -u <이름>     하나 떼어내기

시스템이 부팅한 디스크는 절대 건드리지 않고, nosuid,nodev 로
마운트합니다 - 남의 기계에서 쓴 파일시스템이니까요.

/media 는 임시 자리입니다. 재부팅을 넘겨 계속 같은 자리에 있어야
한다면 입양시키세요.

  storage                          재부팅을 넘겨 남는 곳과 남은 용량
  storage adopt /dev/sdb photos    /mnt/photos 에 고정
  storage format /dev/sdb backup   지우고 ext4 로 만든 뒤 고정
  storage forget photos            그만두기

입양한 드라이브는 장치 이름이 아니라 파일시스템 레이블로 찾습니다.
그래서 다른 포트에 꽂아도 같은 자리에 붙습니다 - sdb1 은 다른
드라이브를 먼저 꽂는 순간 sdc1 이 되기 때문입니다.

poweroff 는 /data 를 언마운트하기 전에 이 드라이브들을 먼저
정리합니다. 쓰는 사람이 있으면 떼어내서라도 - 드라이브 하나 때문에
기기를 끌 수 없게 되면 안 되니까요.


소스는 어디에 있나
------------------
전부 main 브랜치에 있습니다. 아키텍처별로 소스를 나누지 않았습니다.
arm64 와 amd64 가 같은 코드로 빌드됩니다.

  userland/     자체 C 라이브러리, init, 셸, 108개 명령어
    libc/         C 라이브러리. 시스템 콜 위에 바로 올렸습니다
    sh/           셸
    init/         pid 1
    guard/        감시 데몬. CPU, 메모리, 온도, 전압
    <이름>/       명령어 하나당 디렉터리 하나
    mkrootfs.sh   루트 파일시스템 조립
  kernel/       커널 설정과 빌드 스크립트
    lp-zero.config         arm64 (라즈베리파이)
    lp-zero-amd64.config   amd64 (PC)
    build.sh               initramfs 를 넣어 커널을 빌드
  tools/        이미지 조립, SDK, 패키지 빌더, QEMU 실행
    mkdist.sh     배포 이미지 세 개를 한 번에
    mksdcard.sh   카드 이미지 하나 조립
    run-qemu.sh   로컬에서 부팅
  tests/        selftest.sh - 기기에서 도는 51개 검사
  boot/         FAT32 부트 파티션에 들어가는 것
  packages/     패키지 정의
  docs/         설계 메모
  GUIDE/        이 폴더
  dist/         미리 빌드된 이미지

저장소 최상위의 README.md 가 긴 설명입니다. 명령어 하나하나가 무엇을
하는지, 왜 안 죽는지, 보안 모델, 알려진 한계까지 들어 있습니다.
같은 문서의 영어판이 README.en.md 입니다.


직접 빌드하기
-------------
  sudo apt install clang lld llvm gcc-aarch64-linux-gnu \
       mtools dosfstools e2fsprogs xz-utils zip cpio bc \
       bsdextrautils qemu-system-arm qemu-system-x86 python3

arm64 (라즈베리파이 + arm64 VM):

  ./tools/fetch-kernel.sh      # 리눅스 소스
  ./tools/fetch-blobs.sh       # 라즈베리파이 GPU 펌웨어
  make                         # 유저랜드
  make kernel                  # 커널 + initramfs
  make sdcard-linux            # sdcard/lp-zero.img

amd64 (PC) - 네이티브라 크로스 컴파일러가 필요 없습니다:

  make ARCH=amd64
  ( cd userland && LP_ARCH=amd64 LP_BINDIR=bin-amd64 \
      LP_ROOTFS_DIR=rootfs-amd64 \
      LP_CPIO_NAME=initramfs-amd64.cpio.gz \
      LP_HOSTNAME=linux-lp LP_OS_NAME=linux-LP ./mkrootfs.sh )
  LP_ARCH=amd64 LP_ROOTFS_DIR=rootfs-amd64 ./kernel/build.sh
  LP_ARCH=amd64 LP_ROOTFS_DIR=rootfs-amd64 \
      ./tools/mksdcard.sh --linux --uefi-only

배포본 세 개를 한 번에:

  ./tools/mkdist.sh            # 또는: mkdist.sh amd64 | sd | utm

빌드 중간 산출물은 저장소 옆 .build/ 에 쌓입니다. 디스크가 좁으면
LPZERO_WORK=/mnt/big/lpzero 로 옮길 수 있습니다.

업데이트 서명 키는 한 번만 만들면 됩니다. 개인키는 절대 기기에 넣지
마세요. keys/ 는 .gitignore 에 있습니다.

  ./tools/sign-release.sh --new-key
  make
  ./tools/sign-release.sh kernel/out/Image


빌드 확인하기
-------------
tests/selftest.sh 는 기기 위에서 돌면서 검사마다 PASS 또는 FAIL 을
한 줄씩 찍습니다. 부팅, 저장소, SSH, 파이썬, 그래픽, 보안, 오류
경로, 리다이렉션, 로깅, 시간, 그리고 워치독이 코어를 붙잡은
프로세스를 알아채는지까지 봅니다.

  sh /경로/selftest.sh

이 글을 쓰는 시점에서 amd64 이미지 기준 51개 전부 통과합니다.
